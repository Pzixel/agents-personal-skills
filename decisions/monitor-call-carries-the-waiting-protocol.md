# The Monitor call carries the waiting protocol as hook context

Decision: a PreToolUse hook on the `Monitor` tool (`orch/hooks/monitor-wait-note.py`) adds one paragraph to every Monitor call: print only the lines the agent would act on (for a job that checks itself, its terminal event: done, FAIL, process gone, timeout); a progress line is noise; a monitor that prints progress is stopped and re-armed on the terminal event; while it runs, the goal's next item that does not wait on the job starts in the same turn. The hook never blocks. The always-on text is unchanged.

Why: session 2026-10-21 (private retro-evals CASE-28, K40). Under an active `/goal` with three conditions, the main session started an approved production backfill script that gated every step itself and stopped with `FAIL` on the first failure, then armed a Monitor on `tail -F log | grep` with a long list of progress patterns. It woke ten times in three minutes, answered each with one line of narration, and started no independent goal item. Owner: «чем ты сейчас задян? По виду ничем полезным, просто будишься по кд ерундой». Both relevant rules (one monitor per subject without heartbeat wake-ups; do every independent step now) were in the loaded always-on text, so the defect is placement, not wording.

Compared against:
- Rewording the always-on lines: the lines were loaded and not applied; the retro method fixes a loaded-but-unapplied rule by placement. Rejected.
- A refusal (deny) on Monitor commands that look like progress feeds: deciding "progress" from a shell command (`tail -F | grep` alternation lists, loops that echo per step) is a heuristic with false blocks on legitimate terminal-only greps; the note costs one extra TaskStop when the agent got it wrong. Rejected for now; revisit only with live evidence that the note is ignored.
- Text harness, 2026-10-21, one blind grader, both arms in one call, k=3. Round 1 packet (script markers and an author hint about the unopened UI quoted): baseline 3/3, non-discriminating. Round 2 packet (the plan's facts only, Monitor described as the tool describes itself): baseline 0/3 (all three monitors fire on gate/step/ATTACH lines; one defers every goal step until after the job), with the note 3/3. Controls CASE-16 (waits) 3/3 → 3/3, CASE-5 3/3 → 3/3. Accepted by the pre-registered rule.

Live check, fresh headless sessions: with the plugin loaded the session quotes the note's first words back after a Monitor call; on the previous master it answers NONE. Synthetic self-gating job (8 steps, a gate line per step) with an independent second goal part, k=3 per arm: without the hook 3/3 quiet monitors and the independent part done (the prompt names the independence, so the arm does not discriminate); with the hook 3/3 end quiet, two of three first armed a monitor matching `gate`, then stopped it and re-armed on `job done|FAIL`, which is the note's corrective path.

Size: one hook file (static text), one `hooks.json` entry, always-on text unchanged.
