# A changed check is traced to every path that reaches the guarded thing, and lands where they all pass

Decision: when a change adds or tightens a check or rule on one path, the builder first lists every path that reaches the thing the check guards (callers read by eye or language server), the check plan covers each listed path with a test, and the rule lands at the one point all of them pass (a type's constructor, the shared entry), never at the path the task named. A second constructor or a parallel lenient path kept for one record or one flow is a defect: the record is fixed or its removal planned. The property lives in `rules/always-on.md` (Scope); the mechanism in `orch/agents/builder.md` (DESIGN.md content, test-gap checklist item 3) and `orch/agents/reviewer.md` (Coverage lens).

Why: session 2026-10-20/21 (private retro-evals CASE-26, K38). A Reply-all fix put the address split inside the reply mapper; the new-message method of the same class, 45 lines above in the same file, kept sending the raw To string. Plan, design, design review and two code reviews were all scoped to «Reply-all»; nobody asked which other paths hand a recipient string downstream. The bug sat on production ~6 h until the next prod test. Same session, second instance: a stricter address parser was added as a second constructor for the import path only, so that one self-made broken stored record kept decoding; the type stopped guaranteeing a single address. Owner: «проверить ГЛАЗАМИ (либо через language server) какие вызовы вызывают текущую проверку, из этого составить план проверок; сделать новые правила проверки глобальными, а не костылить специальный кейс только под тот один флоу».

Compared against:
- Checklist item 3 as it was («every caller of a changed signature»): a signature did not change in either instance, so the item fired as «to do» and never listed the sibling path. Rejected: it names the wrong trigger.
- A per-prompt hook or a merge-gate field: the decision point is before code (design review), where no gate runs; the existing design-note bullet is the step that fires there. Rejected for now; unmeasured.
- Text harness, 2026-10-21, one blind grader, k=3 per arm: baseline 0/3 (all three read the callers, two centralise the rule, none plans a check per listed path), with the Scope bullet 3/3. Controls CASE-23 and CASE-5: see `runs/callers-line/RESULT.md` in private retro-evals.

Size: always-on +92 words / 571 characters, nothing removed; the layer grows because the design-note bullet names what the note holds and this adds one item the previous wording did not cover. Live check: the next task that tightens a check, in a fresh session — the DESIGN.md names the caller list and the rule's single point before the first code commit.
