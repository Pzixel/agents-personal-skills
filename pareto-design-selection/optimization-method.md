# Optimization method

Applies to every task whose goal is a number: throughput, cost per unit, CPU, memory, disk, a latency budget. Domain does not matter.

- Before designing for a number: name the number at the customer boundary and its unit, the cheapest run that produces it, and the ceiling of the slowest resource with its headroom factor. Decide the store and the cardinality first; per-unit arithmetic inside the store you already have comes after that decision, never instead of it. A pilot costs at most ~10 % of the task's time budget and states which numbers it proves and which it does not.

- Name the unit of work first: the thing the customer counts at the system boundary. The only comparison axis is units per second, or resource per unit, at that boundary. A number of one part (a stage, a service, a queue) is a diagnostic; never offer a choice built on it.
- Before profiling, designing or simulating, produce the unit-cost table: one row per expensive operation (transactions including reads, durable records, bytes, broker sends, objects, network sessions, external calls, CPU time); columns: minimum per unit required by the contract, actual per unit measured on the real system over a run window, gap, projected total at target load. Rank rows by projected gap; fix the top row first. A count from code is a hypothesis; the measured number includes every write whose size grows with state. A breakdown by latency at today's load hides the gap: rank by resource per unit at target load.
- Derive the minimum per unit with three questions per operation: is it needed for the unit to count? can it ride in an operation that already happens? does it carry data nobody reads? Derived data is computed from batches or served by the store built for it, never written per unit into the transactional store. The candidate set always contains the minimum-facts design built from zero, not only trims of the current model.
- An improvement counts when it changes the number of operations per unit or the set an operation ranges over; the N in O(N) can shrink without changing the O. Constant-factor work (faster code, more instances, bigger cache, more hardware) comes after every cardinality gap is closed. Hardware is never the limit without a measured saturation run; while a code fix exists, hardware is a stopgap labeled as debt with the price of the real fix. When a shared resource cannot carry the target, ask first why the work needs that many operations per unit.
- Prove the target number with the thinnest end-to-end prototype on the real path and real traffic (behind a switch, minimal guarantees, within hours), then add guarantees one at a time. A simulation only screens, and only after it reproduces one real run.
- Load tests: each doubling of concurrency must roughly double throughput; the first clearly sublinear step is the finding. Stop doubling, keep the level that holds, find the bottleneck through a probe and fix it to the target. Never re-create running work just to hit an exact count.
