# Redis performance advice, audited on Dragonfly v1.34.0

Verdicts: **helps** / **neutral** / **harms** / **absent** (the feature does not exist) / **unverified**
(plausible but not measured here — do not act on it without measuring). A Redis source is never the
evidence for a verdict; it only states the advice being audited.

| Redis advice | Dragonfly verdict | evidence |
|---|---|---|
| "Prefer pipelining over Lua; scripts are the slow path" `[S23]` | **helps** in regime (a) only — true on default flags, inverted when the script is shard-local | 64 `GET` on 64 keys in one hashtag, 2048B, n=200: one atomic script p50 1860 µs vs one pipeline round trip 480 µs on default flags (3.9x worse), but 186 µs vs 446 µs under `--lock_on_hashtags` (2.4x better). Writes: 2379 vs 1419 µs default, 175 vs 397 µs under the flag `[lab Q11a][S1]`. Mechanism: squashing a pipeline is itself a CPU hot path (`SquashPipeline` ~20% CPU in the maintainer's pprof) `[df-doc issue #6006][S12]`, while a shard-local script pays no hops at all `[df-src EvalInternal][S2]` |
| "`MULTI`/`EXEC` is cheaper than `EVAL` for a few commands" `[S23]` | **helps** sometimes on default flags — never under `--lock_on_hashtags` | same cell: `MULTI`/`EXEC` p50 1026 µs (GET) and 981 µs (HSET) vs script 1860 / 2379 µs on default flags; under `--lock_on_hashtags` `MULTI` is 460 / 472 µs vs the script's 186 / 175 µs `[lab Q11a][S1]`. MULTI/EXEC squashing is disabled when the block runs a script `[df-src Service::Exec][S2]` |
| "One `redis.call` per item is fine, the script runs server-side" | **harms**, and this is the dominant cost in regime (a) | 192 calls -> 6 multi-arg calls: p50 5846 -> 539 µs, p99 9295 -> 1920 µs (standalone, default flags, 2048B, n=200) `[lab Q2][S1]`; on a production script, p50 41183 -> 7814 µs with identical replies `[lab Q7][S1]`; back-to-back ratios 9.9x (default) / 2.0x (`--lock_on_hashtags`) and 7.6x / 2.6x `[lab Q10][S1]`. Inside a genuinely single-key script it is only 1.2x `[lab Q1][S1]` |
| "Avoid hashtags, they create hot slots" | **helps** — and matters more here than on Redis | a tag is a heat unit `[df-doc][S15]`; under `--lock_on_hashtags` with 4 loaders on one tag, an unrelated trivial `EVALSHA` goes 81 -> 7712 µs p50 `[lab Q11d][S1]` |
| "Add a hashtag so the script's keys co-locate" `[S19]` | **neutral** on default flags — the advice is inverted there; helps only with `--lock_on_hashtags` | 256 `HGET`, 2048B, n=200: 8 keys in ONE tag = 26.95 µs/call and `eval_io_coordination_total +1`, identical to 8 keys in EIGHT tags (27.00 µs/call). The hop probe agrees (25.26 vs 23.17 µs/call for 1 vs 4 tags). With `--lock_on_hashtags` the one-tag script flips to shard-local at 1.54 µs/call `[lab Q5][S1]`. Under `--cluster_mode=yes` co-location is a **correctness** requirement (one CRC16 slot per script) `[df-doc][S16]` |
| "Collapse many small keys into one hash to save memory" | **harms** slightly on Dragonfly | 100,000 x 64B on a freshly restarted server: 100k string keys cost **83.7 B/value** vs **109.6 B/value** as one hash of 100k fields and the same 109.6 as 1000 hashes of 100 fields; single-value read p50 is 146-149 µs in all three layouts (default flags, n=200) `[lab Q11b][S1]`. Mechanism: the dashtable's per-key overhead is ~18.6 B against Redis's 32-48 B, so the Redis motivation mostly disappears `[df-doc][S14]`. Collapse for *atomicity or co-location*, not for memory |
| "Use `disable-atomicity` (non-atomic multi) for contended keys" | **harms** in regime (b); pointless in regime (a) | it forces mode `NON_ATOMIC` and `CanRunSingleShardMulti` rejects anything that is not `LOCK_AHEAD` `[df-src][S2]`. Measured under `--lock_on_hashtags`, 8 keys/1 tag, 256 `HGET`: 1.5 -> 30.3 µs/call; it even takes a **1-key** script off the shard-local path (counters `0.00/1.00`). On default flags the script was already io-coordinated, so latency does not move `[lab Q5][S1]` |
| "Let each worker `SCRIPT LOAD` at boot; it is cheap" | **neutral** idle — harms under load | fresh-text `SCRIPT LOAD` of an 8894B script: p50 499 µs idle and 478 µs under 4 loaders on default flags, against 162/149 µs to re-load an already-cached sha; under `--lock_on_hashtags` with 4 loaders it is 7787 µs `[lab Q11d][S1]`. It borrows one of the 10 per-thread interpreters and on v1.34.0 holds it across a journaling hop (contended mean 620.78 -> 259.90 ms after the post-1.34 fix) `[df-doc PR #8300][S11]`. Load once per process; keep NOSCRIPT reload-once `[S25][S27]` |
| "Declare `#!lua flags=no-writes` so the script can run on replicas / under OOM" `[S22]` | **absent** — and the shebang itself breaks the script | `#!lua ...` is a **Lua syntax error** on Dragonfly (`unexpected symbol near '#'`), not a no-op; the directive is `--!df flags=...` `[lab Q9][S1][df-src script_mgr.cc][S3]`. Only `disable-atomicity` and `allow-undeclared-keys` do anything; `no-writes` parses and is ignored `[df-src][S3]`. `allow-oom`, `allow-stale`, `no-cluster`, `allow-cross-slot-keys` do not exist `[df-src][S3]` |
| "Use `redis.setresp(3)` / Redis Functions / `SCRIPT KILL` for runaways" | **absent** | probed on v1.34.0: `redis.setresp` is `nil` and calling it errors; `FUNCTION LIST`, `FCALL`, `SCRIPT KILL`, `SCRIPT STATS`, `MEMORY DOCTOR`, `LATENCY HISTORY` all error `[lab Q9][S1][df-doc][S9]`. There is no script timeout and no BUSY reply: a runaway pins its thread until `kill -9` `[df-doc issue #8269][S10]`. `redis.replicate_commands` exists as a no-op — Dragonfly replicates script *effects* `[df-src interpreter.cc][S4]` |
| "Implement rate limiting in Lua (sliding window / GCRA)" | **neutral** on latency — so use the native command | a 4-`redis.call` sliding window on ONE key costs p50 131 µs vs `CL.THROTTLE` 150 µs on default flags and 99 vs 118 µs under `--lock_on_hashtags` (n=200) — the Lua version is 0.9x / 0.8x, i.e. within noise of the native command while costing an interpreter slot and a script contract `[lab Q11c][S1]`. `CL.THROTTLE` is a single-key `FAST` write command: zero hops, zero interpreter slots `[df-doc][S13]` |
| "Send read-only scripts to a replica" | **unverified** — not measured; `EVAL_RO`/`EVALSHA_RO` do exist | `EVAL_RO` exists and rejects writes at call time `[lab Q9][S1][df-src main_service.cc:1358][S2]`, but no lab cell ran a script against the replica, so there is no Dragonfly evidence for the routing advice. What *is* measured is the replica's cost on the primary: with a replica attached, the per-call write script is +4.3% (mean p50 4679 vs 4484 µs) and the **batched** one +41.6% (569 vs 402 µs), both beyond the spread between replicates of the same condition `[lab Q6][S1]` — the cheaper the script, the more replication dominates |
| "Wrap `MGET`/`MSET` in Lua to make them one operation" | **neutral** | a multi-key command is already split per shard and executed on the relevant threads, so a 3-shard `MGET` costs what 3 hops cost either way `[df-doc][S18]`. Lua adds an interpreter slot and a script contract for nothing unless the keys co-locate |
| "Raise the pipeline depth to amortize round trips" | **unverified for scripts; `--pipeline_squash` is a separate knob** | pipeline squashing is a client-connection mechanism unrelated to MULTI/Lua `[df-src dragonfly_connection.cc][S8]`, and its CPU cost is the subject of an open redesign issue `[df-doc issue #6006][S12]`. No lab cell varied pipeline depth |
