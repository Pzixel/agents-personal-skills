# Always-on rules: Claude Code

Supplements [`always-on.md`](always-on.md) with Claude Code mechanisms; Codex does not load it. `install.sh claude` imports it into the user-level `CLAUDE.md`. Procedures: [`always-on-claude.details.md`](always-on-claude.details.md) in this directory, read when the rule applies or a hook refuses.

<!-- BEGIN owner only -->
## Memory

- A `user` or `feedback` memory that holds outside this repository goes into the user-level rules file (`~/.codex/AGENTS.md` or `CLAUDE.md`) as one line (merge with an existing line, keep its scope); otherwise into project memory. One owner per fact. A one-off request is not a global rule.
<!-- END owner only -->

## Past sessions

- A past Claude Code session named by ID, ID prefix or name is located and read with `~/.claude/tools/chat` (`find`, `humans`, `assistant`; `--help`), never with an ad-hoc transcript parser.

## Hooks and gates

<!-- BEGIN owner only -->
- A plan goes to the owner only when it opens with three plain lines, `Task:` (what is made and what the requester will do with it), `Done when:` (the one observation, at whoever uses the result, that shows it does that job) and `Existing:` (what the project already has for each thing the plan defines, with path:line); `plan-simplify-gate` refuses ExitPlanMode without them; details "Gates".
- A question to the owner (AskUserQuestion) that offers how to define, count or label something, or which mechanism to build or use, carries in its stem a line `Existing:` with what the project already has for it (path:line); `ask-existing-gate` refuses it otherwise. A question that commits money actually charged to us (a purchase, a rent, a paid outside service or metered key; consuming an already paid subscription is not) is one question whose stem carries `Spend: <sum>, ceiling <max>; account: <where>, left <balance>; later: <charges or none>`; the same gate refuses it otherwise; details "Gates".
<!-- END owner only -->
- Hooks enforce the gates; obey a refusal's message, never work around it. The merge command carries `CHECK_RAN: <what ran, result>`, `PROD_POSITION: <blast-radius dimension, production's number, source>`, `WAY_BACK: <undo, minutes>` and `WORSE_FOR: <who gets worse or can break for every consumer, the new bottleneck; or none, with the reason>`, plus `ALWAYS_ON:` when it changes an always-on rules file, or `merge-gate` refuses it. The Stop hook `reply-lint` returns once a reply that leaves a choice or answer to the owner in plain text (decide it, or ask through AskUserQuestion with self-contained options), a completion claim without its observation, a reply that ends on a step of my own while no task, Monitor, one-shot Cron pending its time or agent of the session is live, a reply that lists a lever speeding up a step before naming who consumes that step's result, a reply that names a step of my own at a time that has not arrived while nothing wakes the session on a clock, and a reply whose first paragraph states a cause without opening in the full `Proven:` form, at most twice per turn even on a later stop (details "Gates").
<!-- BEGIN owner only -->
- An owner question is raised with one `PushNotification` whose message starts `QUESTION:` and carries the question and the recommended option; the `open-question` hook pins it to the status line until AskUserQuestion, a typed owner message or a stop with nothing running clears it, after which whatever is still open is raised again. The question is pinned even when the tool answers that it was not sent because the owner is at the terminal; only the main session raises one. It blocks through AskUserQuestion at the point where a wrong guess stops being cheap to discard, or when no independent work is left. `ask-existing-gate` refuses that dialog while no tool call ran since the push, until work runs or `metadata.source` carries `blocked: <why nothing can run without the answer>`; details "Gates". A question that owes a `Spend:` or `Existing:` line is answered only through AskUserQuestion: a notification may announce it while independent work runs, and an ordinary-message answer to it is not consent to the spend.
- A turn that hands control to the owner ends with a message that describes the blocker in full (what it is, what clears it), never by pointer to an earlier message. When the blocker is the owner's answer, ask it through AskUserQuestion with each option self-contained, recommendation first, the question and options in the language of chat replies, since the question is a reply and not an artifact; an action only the owner can perform (a typed `APPROVE <hash>`, a `!` command) stays text with the exact action.
<!-- END owner only -->
- Destructive commands are classified by the hook, never by the agent; the hook's refusal names the class and the step (details "Destructive").
<!-- BEGIN owner only -->
- One monitor per subject, stopped when its work ends, never duplicated, no heartbeat wake-ups. Before ending a turn with background work, a monitor is armed on that exact run; a restarted job needs a new one; the Stop hook `background-watch-gate` returns once a turn that ends with a background task open and no live Monitor or later `CronCreate` on it. A wait is a tool contract (details "Waits"), never an LLM ending its turn to wait: a condition is one Monitor; a clock time, or a wait longer than one Monitor, is one `CronCreate` one-shot (session-only), never a poll script, a sleep or a chain of monitors. A reply that promises a later action by the agent names that mechanism, its id and fire time, how the owner can see it (`CronList`) and what kills it (session exit).
<!-- END owner only -->
- `secret-vault-gate` refuses direct reads of the vault, Secret payloads, and known values in tool inputs; `redact-secrets` masks known values in tool results (details "Secrets").
- `loop-cost-gate` counts, per repository and across the main session and every agent, the minutes waited on long Bash commands (120 s or more), keyed by the program or script a command runs; another launch of a key is refused once that key, since its last acknowledgement, ran long 3 times, or ran long twice while all long commands of the repository since the latest acknowledgement took 30 minutes. Answer with a line `# LOOP_COST: <reason>` in the command naming the incremental form (resume from a saved point, the affected target only, one full run as the gate before merge) or why none exists (details "Gates").
- `no-poll-gate` refuses a script or binary of the session left running past the call (detached with nohup, setsid or `&` in any form, or in `run_in_background`; a later kill or wait of that job in the same call exempts it) without a line `# OUTCOMES: <outcome> -> <step>; <outcome> -> <step>` naming at least two outcomes that lead to different steps; a run whose every outcome leads to the same step is not run, report the fact already in hand instead.
- `wait-shows-gate` refuses a `CronCreate` one-shot, a `Monitor` or a background `wait-for` with a horizon of an hour or more without a line `WAIT_SHOWS: <the fact only this event produces; why one pure function on stored data cannot answer it; why the refactor that would is impossible or beyond the budget>`; `nothing` is refused too: the function runs on today's rows now and is the check.
- The destructive hook reads, before every `kubectl exec`, the target container's memory limit and working set and refuses when the started process cannot fit (a JVM: its `-Xmx` plus overhead; a JVM with no heap cap in the command: always); run such a process outside the pod (a throwaway client pod with its own limit, a local client over a port-forward), or state the heap and add a line `# HEADROOM: limit <L> use <U> adds <A>` for a process sized to fit.
