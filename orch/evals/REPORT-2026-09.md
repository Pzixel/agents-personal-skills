# First full eval of plugin `orch` (2026-09-28)

## Conclusion

1. Over plain Claude the plugin changes the process, not the outcome: every tier A/C code case reaches `check: passed` in both arms; the with arm routes the work to `orch:senior` and keeps the main session short (7–9 turns against 29–38 on the multi-subsystem, sliced and real-PR cases).
2. That process costs 2.5× the plain run on tier A/C (true $70.0 against $27.5); the eval cases are too small to show what the process is bought for (review, fix rounds, cost to the finished state).
3. Suite over the 14 valid cases: score 0.82, mean Δ +0.33 (+0.42 over the 11 cases that can show Δ), 11/14 cases at ≥0.8, 34/42 perfect with-arm runs.
4. Every one of the 8 failing with-arm runs is a run whose main session never loaded `orch:orchestrate`; all 20 runs that loaded it were perfect.
5. The skill is not reloaded after a resume or compaction (2 loads in 15 checkpoint runs, both where the prompt names the skill), so rules that live only in the skill body — fix round to `senior` (R3), design step for a new PR, product questions to the owner — are absent exactly where long sessions run.
6. Checkpoints 4 and 5 fail 0/3: fix round sent to `orch:implementer`; a requirement question answered and planned around instead of put to the owner.
7. Next: one gate that refuses the main session's first Agent spawn (and first code Edit/Write) until the skill is loaded in the current context, plus a closed `implementer` route and a sharper owner-question rule (P1–P3, not applied).
8. Tier A/C ran with Opus 5.5 as main model, tier B with Fable 5.1; Δ is compared only within a case.

## Failure analysis

**Checkpoint 4 (review findings → rulings → fix round), with arm 0,0,0.** All three runs: no skill load; one message spawns three agents in parallel — `orch:implementer` with the fix round (no `step:` line), `orch:reviewer` for a second branch, `orch:senior` `step: design` for a research task. `run_in_background` was omitted, yet the resumed session started all three as background tasks. Last message: a blocker report that the replay sandbox hides the repositories (expected in a replay). Graders: `senior-step` (`orch:senior` + `step: implement`) and `rulings-in-fix-round` (rulings inside that spawn) both fail because the fix round went to `implementer`. The single passing iteration run (step 4) had the same main model (Fable 5.1), the same graders (unchanged since before it) and no skill load either; it chose `orch:senior step: implement`. Plugin between the two: only the R6 foreground-spawn text; the account also changed. All recorded runs of this checkpoint: 2 → `mid` (before the R1 gate), 1 → `senior`, 3 → `implementer`: 1/6. The gate closed `mid` and the choice moved to `implementer`, which the main session may spawn and whose description says "use for every code-writing delegation". **Verdict: plugin defect** (the step-4 pass was a lucky draw, not a regression).

**Checkpoint 5 (owner question that turns on a requirement), with arm 0,0,0.** No skill load; each run answers the forwarded question, tries read-only verification (`orch:Explore`, `orch:prod-probe` or a direct Bash count) and reports the sandbox as a blocker. All three say the identifier can only come from the vendor's API, then either declare the plan changed ("the first priority changes: reconcile the API with our send events") or propose the API route; none asks the owner whether the identifier is needed at all. The without arm does the same. The grader matches the recorded session (answer, then ask the owner and recommend dropping it) and the skill's rule 4 (product questions to the owner before implementation; the history grants no autonomy). **Verdict: plugin defect** — the behaviour is wrong, the grader is right.

**Checkpoint 2 (sizing: a new incident-fix PR), with arm 1,0,1.** The failing run did not load the skill, wrote the spec inline and spawned `orch:senior` with `step: implement` for a PR that has no approved design; the two passing runs loaded the skill first and spawned `step: design`. Both graders fail on that one line. **Verdict: plugin defect** (same root cause).

**`mid-order-class` run 2 (0.6).** `senior-owns` failed: the main session did not load the skill and wrote the three helpers and tests itself (10 turns, check passed, $0.23 against $0.44–0.54 for the passing runs). The outcome is right and cheaper; only the routing rule was skipped. **Verdict: plugin defect, low impact** (skill trigger miss, 1 of 3).

## Proposed changes (not applied; owner decision)

- **P1 — skill-before-work gate (checkpoints 2, 4, 5, `mid-order-class`).** Extend `skill-load-gate`/`agent-type-gate`: in the main session, refuse the first `Agent` spawn and the first `Edit`/`Write` of a code file when `orch:orchestrate` has not been loaded since the last compact boundary of the current transcript; reason: "Load /orch:orchestrate first: after a resume or compaction its rules are not in context." Cost: one refused call per session; one-line edits exempt so the negatives keep passing.
- **P2 — fix rounds cannot bypass `senior` (checkpoint 4).** `spawn_rights.main.deny.implementer`: "Ruling R3: a fix round or any code delegation from the main session goes to `orch:senior` with `step: implement`." Change the `implementer` description from "Use for every code-writing delegation" to "Spawned by `phase-lead` for one bounded phase; the main session delegates code to `senior`."
- **P3 — requirement questions (checkpoint 5).** Add to rule 4 of the skill: "When answering shows that a requirement needs work its requester may not expect (a new integration, a new data source), put the requirement itself to the owner — 'is X needed at all? getting it means Y' — in the same reply, with a recommendation. Answering the question or verifying facts does not replace asking; nothing is planned for X until the owner answers." P1 is what brings this text into context in a resumed session.
- **Graders:** none changed. If the owner prefers in-place work for closed ≤150-line tasks, that is a rule change (R4) first and a `mid-order-class` grader change second.

## Structural limits

- `bugfix-with-check` and both negatives cannot show Δ: their graders pass in both arms by design.
- Process graders need `orch:*` agents the without arm does not have, so part of every Δ is by construction; the arm-neutral outcome grader (`check-passed`) is equal in both arms on every tier A/C case.
- One real-PR case only, and only a Python repository runs inside the sandbox.
- History-file (tier B) cases inherit the main model from the transcript; resumed sessions start spawns in the background regardless of `run_in_background` and write no transcript under `config/projects`.
- The harness prices Opus lower than the usage-audit table.
- Two invocations started in the same second write one results file; the later overwrites the earlier (seen twice on 2026-09-28).
- A usage-limit refusal ("reached your … limit") scores 0 in 1 turn without `partial`; it has to be filtered by hand.
